- Summary (facts, not assumptions):
  - `code_review.api.review(host, ReviewRequest) -> ReviewResult` runs `AgentName.reviewer` as a bounded multi-turn tool loop on `host.llm().run_tool_loop`. It persists the AgentRun, transcript and outputs through the host. Functional findings use `kind=functional`. Statuses come from executed tests: `validated` = the generated test fails with an assertion twice on head AND the rule is `confirmed`. Unconfirmed rules stay `hypothesis` and set `ReviewStatus.needs_clarification`.
  - `propose_repair(host, finding_id, approval_id, repo_id=)` requires an approved `remediation` approval for that finding. It edits only implementation files in an isolated export. A `PatchCandidate` is recorded only after a fresh export + diff + trusted-test replay passes. The finding goes to `patch_proposed`, never `verified`.
  - Security concerns the reviewer notices become `kind=security, status=hypothesis` findings with source spans, history reason `handoff to scout: …`.
  - Evidence: `uv run pytest -q code-review/tests` → 33 passed, 1 skipped (opt-in live). This includes a real-PostgreSQL `AssessmentHost` flow. Provider was FakeTransport throughout; tools (git export, pytest) really executed. **No live-model run yet.**
